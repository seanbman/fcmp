# ADR 0003: Browser is a finite protocol interpreter

Status: Accepted / Phase 2 implementation in progress
Date: 2026-09-10
Plan: `docs/DEVELOPMENT_PLAN_0926-1.md`

## Context

Neith needs rich server-directed interaction without making the browser a second application framework. A generic remote-JavaScript mechanism would reduce apparent implementation work but would create an unsafe, difficult-to-version execution boundary.

The prototype transport also allowed the browser to create a persistent `neith_id` in `localStorage` and sent it in the WebSocket/upload URL. That value was useful as a transport key, but a browser-created identifier is not an appropriate session authority for the framework target.

## Decision

The Neith browser runtime is a finite, versioned protocol interpreter. Protocol messages select known operations with validated payloads. The protocol must not execute arbitrary JavaScript source received from the server.

Forbidden protocol mechanisms include `eval`, `new Function`, unrestricted property traversal/execution, and a generic remote `exec` instruction.

Protocol v1 is explicit on both sides of the wire. Browser messages with a missing/unsupported protocol version or a server-only operation are rejected before handler execution. The current flat Dispatch payload is transitional v1 compatibility surface; Phase 2 will continue toward stricter typed payload validation before the tiny-interpreter refactor.

WebSocket transport uses Gorilla's same-origin policy by default. Cross-origin behavior requires an explicit application policy. Inbound WebSocket messages have an application-configurable size limit with a secure default.

Neith session identity is server-issued. A normal page request establishes a cryptographically random opaque `HttpOnly`, `SameSite=Lax` cookie. Direct HTTPS marks the cookie `Secure`; deployments behind trusted TLS termination may force that flag through application configuration. The browser no longer creates or stores `neith_id`, and session IDs are not placed in WebSocket or upload URLs. WebSocket upgrades and upload requests require the existing session cookie.

The existing named custom-function mechanism is compatibility/advanced surface and must be constrained or replaced by explicit protocol primitives before 1.0.

## Consequences

- Protocol operations become an intentional compatibility surface.
- Go and browser contracts require mechanical drift detection and end-to-end contract tests.
- Unknown versions, operations, and malformed payloads fail closed.
- WSS is necessary transport protection but is not treated as justification for arbitrary code execution.
- Same-origin WebSocket behavior is secure by default instead of permissive by default.
- Session identifiers are generated by Neith and kept out of JavaScript-accessible storage and URLs.
- Upload and WebSocket transport now share the same session boundary.
- Common UI effects should be represented as finite render/mutation/navigation/listener primitives.

## Alternatives rejected

- Sending JavaScript source over WebSocket and evaluating it.
- Growing an unversioned function-name dispatch table indefinitely.
- Moving application behavior into a browser-side Neith framework.
- Trusting a browser-generated localStorage UUID as session identity.
- Accepting every WebSocket Origin by default.

- `dispatch.go`, `dispatch_test.go`: protocol version and inbound operation contract.

- `static/assets/uploads.ts`: same-origin upload path using the HttpOnly session cookie.
- `static/assets/tests/protocol.test.ts`: browser protocol version boundary tests.
